# 节点目录结构规划

## 1. 目的

本文档用于统一节点上的目录规划，明确代码、备份、部署、日志、安装包和持久化数据的存放位置，避免目录混用导致部署、排查和清理困难。

## 2. 目录总览

| 目录 | 用途 |
| --- | --- |
| `$HOME/code` | 代码目录 |
| `/opt/backup` | 备份数据存放目录 |
| `/opt/deploy` | 服务部署目录 |
| `/opt/logs` | 操作日志目录 |
| `/opt/package` | 服务部署包及校验文件目录 |
| `/data` | 持久化数据存放目录 |

## 3. 目录说明

### 3.1 `$HOME/code`

`$HOME/code` 用于存放代码仓库。

使用要求：

1. 代码仓库统一放在该目录下，便于构建、打包和维护。
2. 不应在该目录中存放运行时数据、备份文件或部署产物。
3. 构建生成的安装包应按项目规范输出后同步到 `/opt/package`。

### 3.2 `/opt/backup`

`/opt/backup` 用于存放备份数据。

典型内容包括：

1. 数据库文件备份。
2. 配置文件备份。
3. 重要操作前产生的临时备份。

使用要求：

1. 备份文件应具备可识别的名称，建议包含服务名、备份对象和时间。
2. 备份完成后应确认文件存在且大小符合预期。
3. 备份数据应定期清理，避免长期堆积占满磁盘。

### 3.3 `/opt/deploy`

`/opt/deploy` 用于存放服务部署目录。

当某个服务存在多个版本时，应通过软链接将服务名称指向当前最新版本。

示例：

```text
/opt/deploy/chat-v1.2.3-a1b2c3d
/opt/deploy/chat-v1.2.4-b2c3d4e
/opt/deploy/chat -> /opt/deploy/chat-v1.2.4-b2c3d4e
```

使用要求：

1. 服务版本目录应包含明确版本号或构建标识。
2. 服务名软链接指向当前运行版本。
3. 升级前应保留上一版本目录，便于回滚。
4. 不应直接覆盖已有版本目录。

### 3.4 `/opt/logs`

`/opt/logs` 用于存放操作日志。

使用要求：

1. 部署、升级、备份、清理等操作日志统一写入该目录。
2. 日志文件命名应能体现对应操作或服务。
3. 需要控制日志文件大小，建议单个日志文件不超过 1MB。
4. 对长期运行的脚本，应实现日志轮转或日志截断机制。
5. 不应将业务持久化数据写入该目录。

### 3.5 `/opt/package`

`/opt/package` 用于存放服务部署包以及对应的校验文件。

典型内容包括：

1. 服务安装包，例如 `.tar.gz` 文件。
2. 校验文件，例如 `.sha256sum` 或 `.md5sum` 文件。

使用要求：

1. 安装包文件名应包含服务名、版本号和构建标识。
2. 启用文件校验时，部署包和校验文件应成对保存。
3. 部署或升级前应先校验安装包完整性。
4. 过期安装包应定期清理，但清理前应确认不影响回滚。

### 3.6 `/data`

`/data` 用于存放持久化数据。

数据存放之前必须先创建二级目录。

示例：

```text
/data/mysql
/data/redis
/data/minio
/data/<service-name>
```

使用要求：

1. 禁止直接将数据文件散落在 `/data` 根目录。
2. 每类数据或每个服务应使用独立二级目录。
3. 二级目录名称应能明确体现服务或数据类型。
4. 持久化数据目录应纳入备份和容量监控范围。

## 4. 操作建议

1. 部署前确认所需目录已经存在，并具备正确权限。
2. 备份、部署、日志、安装包和持久化数据应分目录管理。
3. 临时文件使用完成后应及时清理，避免混入正式目录。
4. 清理目录前应确认清理对象、影响范围和回滚需求。
5. 生产环境目录清理应遵守运维操作指导，原则上通过告警触发并人工执行。
